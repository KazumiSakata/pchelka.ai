# Технический контракт и внедрение

## Границы поставки

Поставляется один контейнер для пилота одной организации: интерфейс + API + OCR + SQLite. Он слушает только `127.0.0.1:8000` на хосте. Никакие товары не отправляются в реальные системы РСХБ, маркетплейсы или сторонние модели. Размещённый сайт — статическое демо, серверный API запускается из архива локально.

Приложение не требует ключа LLM. Для внедрения в банковский контур заменяются авторизация, хранение и очередь, но структура карточки и открытый контракт могут сохраняться.

## API 1.0

Авторизация: `Authorization: Bearer <API_TOKEN>`. Не вставляйте ключ в URL или браузерное хранилище. В текущем пилоте все обладатели ключа принадлежат одной организации и обладают одинаковыми полномочиями. Не выдавайте ключи нескольким независимым организациям.

Спецификация: `dist/openapi.json`, а у локального сервера также `GET /api/v1/contract` с Bearer-ключом. `/api/openapi.json` — открытая схема без данных и секретов. `/api/docs` использует стандартный Swagger CDN, но строгая CSP запрещает сторонние скрипты: используйте локальный JSON в своём Swagger/SDK-генераторе.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/health` | Безопасная открытая проверка живости |
| GET | `/api/v1/drafts` | Список карточек единой пилотной организации |
| POST | `/api/v1/drafts` | Multipart: исходники → OCR → кандидаты |
| GET | `/api/v1/drafts/{id}` | Текущая версия, источники, проблемы, журнал |
| PATCH | `/api/v1/drafts/{id}` | Изменение с обязательным revision |
| POST | `/api/v1/drafts/{id}/generate` | Шаблон только из confirmed, создаёт новую версию |
| POST | `/api/v1/drafts/{id}/approve` | Явное подтверждение готовой версии |
| GET | `/api/v1/drafts/{id}/export` | Только approved, иначе 409 |
| DELETE | `/api/v1/drafts/{id}` | Удаление записи и ключей идемпотентности |
| GET | `/api/v1/contract` | Контракт для инструментов интеграции |

POST `/drafts`: `text` (до 8000 символов), `category` (`honey`, `dairy`, `other`), повторяющееся поле `photos` (0–6 файлов). Нужен заголовок `Idempotency-Key` длиной 8–128. Общий запрос ≤62 MiB, файл ≤10 MiB и ≤20 MP, форматы JPEG/PNG/WebP, без анимации. Для POST с тем же ключом и тем же содержимым возвращается тот же draft ID. С другим содержимым — 409. Ключи хранятся до удаления карточки.

```sh
curl -X POST http://localhost:8000/api/v1/drafts \
  -H "Authorization: Bearer $API_TOKEN" \
  -H 'Idempotency-Key: your-unique-request-001' \
  -F 'category=honey' \
  -F 'text=Мёд цветочный, 500 г. Состав: мёд натуральный.' \
  -F 'photos=@label.jpg'
```

Пример поля-кандидата:

```json
{
  "key": "weight",
  "value": "500 г",
  "source": "ocr",
  "image_id": "server-generated-uuid",
  "quote": "500 г",
  "status": "candidate",
  "confidence": 0.91
}
```

`confidence` в текущей версии — среднее Tesseract confidence слов исходного изображения, не оценка конкретного поля и не вероятность достоверности. У исходного текста и ручных значений null. У самого изображения указан `confidence_scope: image_mean_not_field_probability`. Для следующего этапа нужны координаты конкретных токенов и калибровка на целевом наборе этикеток. Цитата и `image_id` показывают происхождение, не подтверждают подлинность.

Каждая характеристика `name`, `weight`, `composition`, `producer`, `shelf_life`, `storage` существует в карточке один раз. Все варианты извлечения остаются в `evidence`. Отличающиеся значения находятся в `conflicts`. Присвоение `confirmed` означает ручное действие продавца через доверенный клиент, а не независимое доказательство.

PATCH должен содержать полный редактируемый снимок, не произвольные поля:

```json
{
  "revision": 1,
  "category": "honey",
  "facts": [
    {"key":"name","value":"Мёд цветочный","status":"confirmed","source":"manual"},
    {"key":"weight","value":"500 г","status":"confirmed","source":"manual"}
  ],
  "title": "Мёд цветочный, 500 г",
  "description": "Описание продавца после проверки.",
  "conflict_resolved": false
}
```

Если значение не изменилось, сервер сохраняет настоящий источник, quote и confidence, игнорируя попытку подделать их клиентом. Новые и изменённые значения получают `source=manual`, `confidence=null`, `image_id=null`. В PATCH все факты должны иметь непустые значения; отсутствующее поле можно не передавать, оно попадёт в список пробелов.

Успешный PATCH повышает revision и снимает approved. `generate` также повышает revision. Пример тела для generate и approve:

```json
{"revision":2,"acknowledged":true}
```

Для generate флаг acknowledged не используется как согласие на публикацию; унифицированная схема оставлена для простоты пилота. Approve требует true, полных обязательных полей, подтверждения всех кандидатов, фото и текста, отсутствия рисков. Возвращает approved без повышения revision, так как подтверждается именно эта версия. Повторное подтверждение той же версии идемпотентно.

| Код | Поведение интегратора |
|---|---|
| 401 | Проверить токен, не повторять автоматически |
| 404 | Карточка отсутствует / удалена |
| 409 | Перечитать revision или исправить Idempotency-Key; export требует approved |
| 413 | Уменьшить исходники; не повторять тот же payload |
| 415 | Заменить невалидное изображение |
| 422 | Показать пользователю ошибки / недостающие поля |
| 429 | Подождать Retry-After при наличии; ограничить очередь OCR |
| 503 | Установить Tesseract и нужные языковые данные |
| 504 | OCR превысил 20 секунд на фото; предложить пересъёмку |

Синхронное распознавание до шести фото потенциально занимает до 120 секунд плюс обработка. Браузерный таймаут — 150 секунд, это не SLA. После сетевого таймаута повторяйте с тем же Idempotency-Key, не создавайте новую карточку без сверки. Пилот не держит долговечную очередь задач; для нагрузки требуется async job API.

## Адаптер витрины

1. В собственном контуре хранить оригиналы в приватном объектном хранилище и выдавать только краткоживущие ссылки после антивирусной проверки. Не передавать публичные URL с секретами.
2. Отправить те же фото в API, сохранить соответствие `sha256 → asset_id` собственного каталога.
3. Прочитать draft и показать пользователю факты и цитаты. Не обходить подтверждение автоматически.
4. PATCH с актуальной revision, при необходимости generate, перечитать результат.
5. Получить явное согласие человека на approve.
6. GET export, проверить `status=approved`, совпадение revision, id и соответствие схеме витрины.
7. Сопоставить внутреннюю категорию и поля с версионируемым профилем витрины. Если её обязательных полей нет, запросить их отдельно, не подставлять defaults.
8. Отдельно подтвердить публикацию в целевой системе. В этом проекте такой вызов не реализован.

Оригиналы в API не сохраняются, после OCR остаются только текст, hash и размеры; retrieve/download изображений не предусмотрен. Поэтому один лишь JSON не является полным фото-пакетом для маркетплейса. В промышленном варианте добавить quarantine/assets API и выдачу приватных объектных ссылок.

## Архитектура промышленного продолжения

Браузер → API Gateway с SSO → Draft service (PostgreSQL) → очередь задач → изолированные OCR workers без egress. Фотографии → quarantine storage → scanner → clean storage; модели читают только clean assets. Policy service хранит профили категорий/витрин. Publication adapter читает только утверждённый snapshot. Отдельный append-only audit stream отправляется в SIEM.

Асинхронный контракт будущей версии: create возвращает 202 + job_id; GET job с pending/running/completed/failed; webhook подписан HMAC с timestamp и event_id, повторная доставка дедуплицируется. В текущем API webhooks и async jobs отсутствуют. Клиентские URL никогда не скачиваются OCR-движком, поэтому канал SSRF через remote-photo URL не создаётся.
